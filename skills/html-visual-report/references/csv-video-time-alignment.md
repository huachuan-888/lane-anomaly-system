# CSV ↔ 视频时间对齐实战 (2026-08 会话沉淀)

生成车道线分析 HTML 报告时，截图时间与错误点时间"逐秒对应"是用户硬性要求。
以下是本会话用真实数据验证过的坑与铁律。

## 1. CSV timestamp 列选择陷阱（最隐蔽）

CSV 表头同时存在多个时间列：
```
[0] timestamp                                  ← 字符串时间 "2026-06-16 10:57:01.164"（要用这个）
[1] lane_mark_camera_list_1.msg_head.sequence
[2] lane_mark_camera_list_1.msg_head.timestamp ← epoch 毫秒 1781578619702（必须跳过！）
```

- 用 `if "timestamp" in col.lower()` 匹配会**选中第 2 列**（epoch 毫秒），
  解析后得到 1781578619702 这样的天数字节 → 时间全乱。
- **正确做法**：`if cl.strip() == "timestamp"` 精确匹配第 0 列；
  显式 `elif "msg_head.timestamp" in cl: continue` 跳过 epoch 列。
- 验证：`sec=39421`（10:57:01）才是对的；`sec=1781578619702` 就是选错列了。

## 2. TS 视频 CAP_PROP_FRAME_COUNT 返回垃圾值

```python
cap.get(cv2.CAP_PROP_FRAME_COUNT)  # TS 容器返回 -192153584101141 这种负数！
```
TS（MPEG-TS）无法直接获取帧数。**不要用它做帧号钳制上限**。
正确方式：顺序 `read()` 逐帧计数（本数据 1503 帧 ≈ 60 秒），
或抽帧时用 `read_frames_sequential` 只读到需要的帧号。

## 3. 视频匹配铁律：vstart ≤ 错误点时间 < vstart+60

```
错误点 b1=10:57:04 (39424s)
视频   10:58:41 起始 (39521s)
帧号 = (39424-39521)*25+3 = -2422 → 负数！
```
- 帧号为负时如果钳制到 0，会截到**视频开头画面**（时间完全不对）。
- **铁律**：`find_video_for_sec` 只匹配 `vstart <= target_sec < vstart+60` 的视频
  （错误点必须落在该视频的 60 秒覆盖区内），找不到就返回 None → 报告显示
  "📭 无对应视频帧"，**绝不硬截错帧**。
- 只写 `vstart <= sec` 不够：若错误点在视频起始后很久（>60s），帧号会超出
  视频长度，同样拒绝。
- 错误点早于视频起始 = 该错误点确实没有视频，这是数据特性不是 bug。

## 4. 一个 CSV(10分钟) ↔ 多个视频(每段1分钟)

- CSV 覆盖 10 分钟（如 10:57:01~11:07:01），视频每段 60 秒（文件名=起始时刻）。
- 视频CSV对应 文件夹每组只放**第一个视频**，CSV 开头 ~100 秒的错误点无视频。
- 完整匹配需用整个视频目录（`视频\6.16|6.17|6.18\`），按 vstart≤b_sec 找最近的段。

## 5. CSV 去重（视频CSV对应结构）

同一 CSV 文件（如 `2026-06-16_10-57-01...csv`）在多个视频组文件夹里都有拷贝。
`find_csv_in_dir` 会找到 49 个路径但只有 17 个唯一文件 → **按文件名去重**，
否则同一 CSV 被重复分析生成多个相同问题卡片。

## 6. 截图时间标签（逐秒对应）

- 三张截图标签用 `b_sec + offset` 计算真实时间（`b-1s 10:57:03 / b0s 10:57:04 / b+1s 10:57:05`），
  **不要**从帧号反推（`int()` 截断会让三张都显示同一秒）。
- 错误点时间用 CSV timestamp（唯一可信时钟），视频水印不可信（开头含旧素材帧）。

## 7. 丢失事件聚合 + 开场缓冲

- 开头 3 秒跳过（感知未就绪，大量假丢失）。
- 连续丢失（间隔 ≤2s）聚合为一次事件，段内只保留丢失标签（丢弃丢失期间的抖动）。
- `range=0` 的槽位是无效占位（id=99），只在 `0 < r < 30` 时判可视范围异常。

## 8. 日期对应铁律（2026-08 用户实测"日期对应不对"后修复）

视频按**日期子文件夹**存放：`视频\6.16\`（22个）、`6.17\`（21个）、`6.18\`（6个）。
**只按 HHMMSS 时间匹配会跨日期误匹配**——不同日期存在相同时刻的视频
（如 6.16 和 6.17 都有 10:58 段），6.17 的 CSV 错误点可能截到 6.16 的视频画面。

正确做法：
1. `csv_date_to_video_dir(csv_path, video_dir)`：从 CSV 文件名提取日期
   （`2026-06-16_10-57-01...csv` → 正则 `(\d{4})-(\d{2})-(\d{2})` → `6.16`），
   在视频目录中找同名子文件夹，只在该子目录内匹配视频。
2. `find_video_in_dir` 的"跳过根目录"逻辑要写成**跳过父级**而不是跳过传入目录本身：
   ```python
   parent = os.path.abspath(os.path.dirname(video_dir.rstrip("\\/")))
   if os.path.abspath(root) == parent: continue
   ```
   否则传 `视频\6.16` 时会把 6.16 本身当根目录跳过，返回 0 个视频。
3. `视频\` 根目录可能有游离视频（无日期归属，如 ND02512_105841），
   用日期子目录匹配后自然排除，不会误用。

验证：6.17 CSV 错误点 10:04:49 → 6.17 无该时段视频 → 正确显示"无视频帧"
（修复前误匹配 6.16 的 10:04 视频，截图内容与日期不符）。

## 9. 问题表驱动（xlsx → 报告，2026-08 实测）

用户有 `V1.1.6版本测试问题.xlsx`（33 个问题）时必须**按问题表生成报告**，
否则用户会问"为什么只有17个问题，问题表不是30多个吗"。

- xlsx 结构：第1-6行元信息（测试时间/车辆/路线/版本），**第7行才是表头**
  `[编号, 日期, 时间点, 问题归类, 问题现象描述, 环境特性, ...]`，第8行起数据。
  读取：`ws.iter_rows(min_row=8, values_only=True)`，`num is None` 跳过。
- 时间格式清洗（实测多格式）：`10:58:00` / `11.06`（点代冒号）/ `17::24`（双冒号）/
  `10：04`（全角冒号）。清洗：`replace("：",":").replace(".",":").replace("::",":")`。
- 关键词筛选会误捕：`"锥桶摆放到车道线上"` 的描述命中"车道线"关键词，把点刹问题#26
  也选进车道线报告（33 → 18 个）。这是预期（与旧系统一致），不是 bug。
- **CSV 文件名正则坑**：`find_csv_for_issue` 用 `(\d{2})-(\d{2})-(\d{2})` 会匹配
  日期前缀里的月-日（`2026-06-16` → `06-16`）而不是时分秒 → 全部匹配失败。
  必须用 `(\d{4}-\d{2}-\d{2})_(\d{2})-(\d{2})-(\d{2})` 并取 group 2/3/4 为时分秒。
- 问题时间 vs 视频起始：问题时间点常比视频起始早几十秒（视频从问题后开录），
  find 窗口放宽 `[vstart-90, vstart+60]`，extract_frames 内仍严格 `[vstart, v_end]`。
- 状态标记：问题卡片 summary 加 `<span class="pdata">CSV✅/❌ 视频✅/❌</span>`，
  用户明确要求"有视频和csv数据你都标注在问题旁边"。

## 10. 错误类型标注 + 窗口重叠过滤 + 规则精确语义（2026-08 会话收尾）

用户验收时问"为什么错误类型你没有标注"、"规则按照我们之前说的那几条"——
这是报告生成的**硬性要求**：每个问题卡片必须显示规则检测出的错误类型标签
（如"右侧丢失"），不能只显示问题时间和截图。

### 错误类型没显示的三层根因（依次修复）

1. **规则窗口过滤把跨窗口事件滤掉了**：`analyze_csv(csv_path, b_sec)` 带 ±30s 窗口时，
   若用简单判断 `b_sec-30 <= p["sec"] <= b_sec+30`，会把**跨窗口的丢失事件**滤掉
   （丢失事件起点 10:57:04，窗口 [10:57:30, 10:58:30]——起点早于窗口左界但事件
   持续覆盖窗口）。结果 17 个问题全部显示"问题时间点(无CSV异常)"。
   **正确**：事件与窗口**重叠**即保留——
   ```python
   p_end = p.get("end_sec", p["sec"])
   if p["sec"] <= hi and p_end >= lo:  # 起点<=窗口右界 且 终点>=窗口左界
   ```
2. **抽帧时间点选错**：若抽帧用错误点事件起点（10:57:04），而视频从 10:58:41 才开始
   → 全部在视频外 → 截图 0 张。**抽帧必须用问题时间点 b_sec**（问题时刻通常在视频内），
   错误类型标签 = 窗口内所有事件的标签**合并去重**后标注在问题时间点下。
3. **labels_map 没绑定到抽帧时间点**：`extract_secs=[b_sec]`，`labels_map={b_sec: merged_labels}`，
   合并逻辑遍历 `points[:10]` 去重收集所有标签。

### 规则引擎精确实现语义（对齐判断标准.txt，勿简化）

| 规则 | 精确语义 | 实现要点 |
|------|---------|---------|
| 规则二 抖动 | \|ΔC0\|≥0.2 **连续3帧**才记一次抖动事件 | `jitter_count[side]` 计数器：满足+1，达3才 append 标签并清零；不满足清零 |
| 规则四 可视范围 | 拆两子条件：**骤降**（≥60→<30 相邻帧）+ **持续短**（<30m 超10帧≈1秒） | `prev_view[side]` 记上一帧值判骤降；`view_low_count[side]` 计数器判持续 |
| 规则四 排除 | `range<=0` 的槽位是无效占位（id=99），不算可视异常 | `if r <= 0: continue`（只记录 prev_view） |
| 规则三 宽度 | W≤3.4 过窄 / ≥4.0 预警 / ≥4.1 降级（持续5帧的持续条件在数据中难严格实现，按单帧阈值近似） | 双阈值 if/elif 链 |

### 无错误类型时的兜底

`points` 为空（窗口内无任何规则命中）时才显示"问题时间点(无CSV异常)"——
这是**兜底**，不是常态。正常车道线问题（#1~#17）都应检出"右侧丢失/左侧丢失"
（实测：右侧丢失17次、左侧丢失2次）。

## 11. 双维度校验按标签类型分派 + 场景识别（2026-08 会话收尾）

### dual_check 必须按 CSV 标签类型分派（用户实测纠正）

用户实测报错："为什么 A=11.06 会 CSV报过宽但画面实测仅0.53m"——旧逻辑
"只要有 CSV 异常就比宽度"把"右侧丢失"标签也拿去比宽度，输出荒谬的
"CSV报过宽但画面实测仅0.53m"（0.53m 是 Hough 暗光下只检到局部线段的垃圾值）。

修复后的语义（务必遵守）：
```
标签含"丢失" → 检查画面有没有线：
    两侧无线 = ✅ 真实异常（丢失属实）
    两侧有线 = ⚠️ 疑似感知误报（画面有线却说丢失）
    单侧有线 = ✅ 真实丢失（用户 2026-08 最后纠正：画面只检到单侧线=另一侧丢失，
               不是"需人工复核"兜底！返回 `✅ 真实丢失: CSV报丢失, 画面仅X侧有线(Y侧丢失)`，
               画面检测描述写 `仅检测到X侧车道线(px), Y侧丢失`）
标签含"过宽/过窄" → 才比较画面实测宽度：
    w≥4.0 或 w≤3.4 = ✅ 真实异常
    3.4~4.0        = ⚠️ 疑似感知误报
    检测不完全/像素<3000/w=None = 🔍 需人工复核
标签为"可视/抖动" → 画面有线时一律 🔍 需人工复核（需多帧/场景判断）
```

### 画面侧丢失标签的追加顺序（用户确认"这个效果还可以 你要保持"）

单侧检测时要把 `画面X侧丢失` 追加为**独立错误类型标签**，和"抖动 ΔC0=3.74m"、
"车道线过宽预警 4.055m"一样显示在 et 标签区——**必须在 `labels_html` 生成之前追加**：
```python
# 循环开头（先检测，再生成 labels_html）
b1_fidx_pre = point_frames.get(pt["sec"], {}).get(0)
if b1_fidx_pre is not None and b1_fidx_pre in video_frames:
    _det_pre = detect_lane_in_frame(video_frames[b1_fidx_pre])
    if (_det_pre["left_ok"] or _det_pre["right_ok"]) and not (_det_pre["left_ok"] and _det_pre["right_ok"]):
        miss_side_pre = "右" if _det_pre["left_ok"] else "左"
        tag = f"画面{miss_side_pre}侧丢失"
        if tag not in pt["labels"]:
            pt["labels"] = list(pt["labels"]) + [tag]
labels_html = "".join(f'<span class="et">{htmlmod.escape(lb)}</span>' for lb in pt["labels"])
```
⚠️ 陷阱：把标签追加放在**后面的双维度校验块**里不会生效——labels_html 已在循环开头
生成，追加的标签只出现在校验说明文字、不出现在错误类型标签区（用户要求"分析完也要
拿出来单独标记出来"）。实测分布：`画面右侧丢失 ×5` 与过宽/抖动标签并列显示。

### 宽度计算的三个守卫（实测踩坑）

1. **Hough 负宽度**：`min(right_xs) - max(left_xs)` 可能为负 → 宽度 -0.98m。
   左线取 `max(left_xs)`（靠右边缘）、右线取 `min(right_xs)`（靠左边缘），
   且 `right_edge > left_edge` 才计算。YOLOP 分支同样 `px > 0` 守卫。
2. **width_m=None 时 f-string 崩溃**：`f"{det.get('width_m', 0):.2f}"` 抛
   `TypeError: unsupported format string passed to NoneType.__format__`，
   程序直接退出（报告不生成）。格式化前必须判 None。
3. **宽度是近似值**：标定系数 3.65m/参考像素是线性近似（透视近大远小），
   0.53m 这类极端值在暗光/局部检测时不可信，宁可不显示。

### 场景/环境识别（用户要求：天气 + 道路环境）

问题卡片必须带场景标签（用户："记得加入天气识别和道路环境识别 隧道 弯道 合流道等"）：
- 天气：问题表"环境特性"列（row[5]）→ `天气:晴/阴/小雨`
- 道路环境：描述文本关键词匹配（SCENE_KEYWORDS 表）：
  `隧道`/`弯道`（弯道/左弯/右弯/急弯）/`分合流`（合流/交汇口/分叉）/`直道`/
  `鱼骨线`/`坡道`/`匝道`/`换道`（换道/变道/拨杆）/`进隧道`（入隧道/隧道口）/`出隧道`
- scene 数组 = `extract_scene(desc) + ["天气:"+env]`，渲染 `<span class="sc">`
- 实测分布：天气:晴8 / 天气:阴9 / 天气:小雨1 / 隧道4 / 弯道2 / 分合流2 / 鱼骨线1 / 换道1
